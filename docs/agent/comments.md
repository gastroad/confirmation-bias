# 댓글

**도입 2026-08-24.** 클러스터(= 그날의 한 이슈)마다 회원이 댓글을 남긴다.

## 클러스터에 매다는 것의 함정

클러스터링은 **하루 1회 전날에 대해서만** 돌아, 한번 만들어진 날짜의 클러스터는 그대로 굳는다.
평상시에는 댓글이 안전하다.

문제는 **같은 날짜를 다시 돌릴 때**다. `clusterDay`는 멱등성을 위해 그 날짜 클러스터를 지우고
새로 만들기 때문에 클러스터 id가 바뀐다. 재실행 경로는 둘이다:

- `/admin`의 "클러스터링 재실행"
- 백필 (`--all`, `--from/--to`)

그대로 두면 그 날짜의 댓글이 통째로 사라진다(`Comment`에 `ON DELETE CASCADE`가 걸려 있다).

### 승계

`successorByOldCluster()`가 **옛 클러스터의 기사들이 어느 새 클러스터로 가장 많이 갔는지**로
후계자를 정하고, 댓글을 그쪽으로 옮긴다. 동수면 새 클러스터 id가 작은 쪽(결정적).

이를 위해 `clusterDay`의 트랜잭션 순서가 바뀌었다:

| 이전               | 지금                               |
| ------------------ | ---------------------------------- |
| 삭제 → 생성 → 배정 | **생성 → 배정 → 댓글 이관 → 삭제** |

**먼저 지우면 CASCADE가 댓글을 가져가 버린다.** 순수 함수라 `daily.test.ts`가 쪼개짐·합쳐짐·
동수 결정성까지 고정한다.

**한계**: 클러스터가 여러 개로 쪼개지면 댓글은 가장 큰 조각으로 간다. 후계자가 없으면(기사가
전부 다른 날짜로 옮겨가는 등) CASCADE로 삭제된다. 완벽한 보존이 아니라 "대체로 따라간다"다.

## 작성자 정보를 비정규화한 이유

`neon_auth` 스키마는 Neon Auth가 관리하고 Prisma 밖이라 **join할 수 없다.** 그래서 작성 시점의
표시명을 `Comment.authorName`에 굳힌다.

- 표시명 = `name` 또는 이메일 로컬파트. **이메일 전체는 저장하지 않는다**(도메인까지 노출할 이유가 없다)
- `authorId`는 `neon_auth."user".id`지만 FK를 걸 수 없다(스키마가 다르다)

## 권한

**삭제 권한 판정을 `deleteComment()`의 `where` 절에 넣었다** — 호출부가 검사를 빠뜨릴 수 없다.

```ts
where: { id, ...(actor.isAdmin ? {} : { authorId: actor.id }) }
```

0건이 지워지면 "없음"과 "남의 댓글"을 구분하지 않고 같은 404를 준다(존재 여부를 흘리지 않는다).

UI의 `canDelete`는 **서버가 계산해 내려준다**(`toComment`). 클라이언트 판단은 버튼을 숨길 뿐
실제 권한이 아니며, 실제 삭제는 위 쿼리가 다시 검사한다.

## 탈퇴 시: 삭제가 아니라 익명화

`anonymizeCommentsByAuthor()`가 `authorId → null`, `authorName → "탈퇴한 사용자"`로 바꾼다.
본문은 남는다.

본문까지 지우면 **다른 사람의 대화 맥락이 끊긴다.** 개인정보처리방침의 "탈퇴 시 파기"와도
일관된다 — 식별자와 표시명이 사라지므로 탈퇴 후에는 그 댓글을 계정과 연결할 수 없다.
방침에 이 처리를 명시했고, 본문 삭제를 원하면 탈퇴 전 직접 지우거나 문의하도록 안내한다.

## 관리자 화면

`/admin/comments` — 전체 댓글을 최신순으로 훑고 삭제한다. 클러스터를 넘나들며 봐야
신고·스팸에 대응할 수 있는데, 그전에는 각 클러스터 상세로 직접 들어가야 했다.

- **권한이 없으면 조회 자체를 하지 않는다.** 화면만 가리면 DTO가 HTML에 실려 나간다.
- 커서는 `createdAt`이 아니라 `id`다 — 같은 초에 여러 건이 들어오면 시각만으로는 경계가
  흔들려 중복·누락이 난다.
- 무한 스크롤 대신 **명시적인 "더 보기"** 를 쓴다. 삭제하면 목록이 밀리는데 자동 로딩이면
  위치가 흔들린다.

권한은 세 겹으로 본다: `proxy`(경로) → Server Action(호출) → `deleteComment`의 where 절(쿼리).
**Server Action은 URL과 무관하게 호출될 수 있어** proxy만으로는 부족하다.

## 남은 것

- **수정 기능 없음.** 지우고 다시 쓰는 방식이다.
- 관리 화면에 검색·필터가 없다. 댓글이 많아지면 필요하다.
- **스팸·도배 방어 없음.** 로그인 필수가 1차 방어선이지만, 공개 후 문제가 되면 rate limit이 필요하다.
- 대댓글·좋아요 없음.
- 댓글 수가 많아지면 페이지네이션이 필요하다(현재 전량 로드).
