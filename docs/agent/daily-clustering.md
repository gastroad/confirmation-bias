# 일별 배치 클러스터링

**전환 완료 2026-08-24.** 증분 배정(도착 순서대로 기존 클러스터에 붙이기) → KST 하루치를 모아
한 번에 응집 클러스터링(HAC).

## 왜 바꿨나

증상은 "갈수록 이상한 데이터끼리 엮인다"였고, 실측하니 **최대 클러스터가 253건**이었다
(그다음 143·112·111·106…). 원인은 두 가지가 곱해진 것이다.

1. **후보 클러스터가 죽지 않았다.** `loadRecentClusters()`가 `updatedAt >= now-48h`로 후보를
   골랐는데, 기사가 붙을 때마다 `updatedAt`이 갱신됐다. 활발한 클러스터는 윈도우를 영영
   벗어나지 못하고 계속 흡수했다.
2. **centroid가 뭉개졌다.** `updateCentroid()`의 가중이동평균은 기사가 쌓일수록 centroid를
   "평균적 정치기사" 쪽으로 끌어당겨, 무관한 기사도 임계값을 넘겼다.

거기에 greedy 배정이라 **같은 날 기사여도 도착 순서만 다르면 결과가 달랐다**.

일별 배치는 셋 다 구조적으로 없앤다. 버킷이 하루로 닫혀 있어 윈도우 누수가 없고, 배치 전체를
보고 나누므로 순서에 영향받지 않으며, centroid를 누적 갱신하지 않는다.

## 알고리즘: average linkage HAC

`server/clustering/hac.ts`의 `agglomerate()`. 순수 함수라 DB·프레임워크와 무관하다.

**average linkage(UPGMA)를 쓴다.** single linkage는 chaining이 심해 A-B, B-C가 가까우면 A-C가
멀어도 한 덩어리가 된다 — 증분 배정에서 겪던 블랙홀이 그대로 재현된다. 이 성질은
`hac.test.ts`의 "average linkage라 chaining이 일어나지 않는다"가 회귀 테스트로 붙잡는다.

입력 벡터는 **정규화되어 있어야 한다**(`vector.ts`의 `normalizeInPlace`). 그 전제 위에서
유사도를 내적으로만 계산해 코사인 대비 3배 빠르다. OpenAI가 512차원으로 잘라 주는 임베딩은
L2 norm이 0.99933~1.00058이라 사실상 단위벡터지만, 오차를 배치 진입 시 한 번 흡수한다.

**복잡도**는 병합 1회당 O(활성²), 최악 O(n³). 실제로는 임계값에서 일찍 멈춰 병합 횟수가 n보다
훨씬 적다(하루 300~700건, 대부분 클러스터가 1~10건). **하루 유입이 2,000건을 넘으면**
nearest-neighbor chain(O(n²) 보장)으로 교체할 것.

## 임계값 0.62의 근거

`server/clustering/daily.ts`의 `DEFAULT_THRESHOLD`. 세 날짜를 0.54~0.70에서 실측해 골랐다.

| threshold | 08-20 (662건) | 08-17 (403건) | 07-15 (518건) |
| --------- | ------------- | ------------- | ------------- |
| 0.54      | 175 / **46**  | 90 / **138**  | 153 / 37      |
| **0.62**  | **250 / 26**  | **143 / 67**  | **217 / 24**  |
| 0.70      | 341 / 19      | 214 / 25      | 292 / 12      |

_(클러스터 수 / 최대 크기)_

- **0.65 이상**: 하나여야 할 대형 이슈가 쪼개진다. 08-17 전당대회 보도 67건이 36건으로 갈렸다.
- **0.60 이하**: 최대 클러스터가 67 → 86 → 138건으로 급증한다.
- 무작위 쌍 유사도는 p50 0.34 / p90 0.48 / p99 0.66이라 0.62는 상위 1% 근처에 놓인다.

**튜닝은 `--dry-run`으로 한다.** DB에 쓰지 않고 크기 분포만 낸다.

```bash
npm run cluster:day -- --date=2026-08-20 --dry-run --threshold=0.65
```

## "최대 클러스터 크기"는 품질 지표가 아니다

전환 설계 때 "최대 클러스터 ≤40건"을 수용 기준으로 잡았는데 **틀린 기준이었다.**
대형 정치 이벤트 날에는 하루 기사의 15~20%가 한 이슈에 정당하게 쏠린다.

- 2026-08-17 · 67건 — 민주당 전당대회(김민석 당선). 그날 기사 403건의 17%
- 2026-07-31 · 85건 — 검찰 보완수사권 폐지 형소법 국회 통과. 필리버스터→표결→반응

둘 다 육안 확인 결과 **오분류가 아니다**. 크기 상한을 강제하면 이런 보도를 인위적으로 두 동강
낸다. 그래서 `agglomerate`의 `maxClusterSize`는 **기본 비활성**이고, 판단은 육안 검증으로 한다.

판단 기준은 "크기"가 아니라 **"무관한 기사가 섞였는가"**다.

## 파이프라인

```
.github/workflows/collect.yml        3시간마다   RSS → Article (임베딩·클러스터링 없음)
.github/workflows/cluster-daily.yml  UTC 20:00   = KST 05:00, 전날 하루를 통째로 클러스터링
```

수집과 클러스터링을 분리한 이유: RSS는 항목이 빠르게 밀려 나가 자주 긁어야 하지만,
클러스터링은 하루가 닫힌 뒤 한 번만 하면 된다. collect는 OpenAI를 부르지 않으므로
`OPENAI_API_KEY`가 필요 없다.

**클러스터링은 멱등하다.** 해당 버킷의 기존 클러스터를 지우고 새로 만들기 때문에 같은 날짜를
몇 번 돌려도 결과가 같다. 늦게 도착한 기사가 있으면 그 날짜만 다시 돌리면 된다.

```bash
npm run cluster:day                                    # 어제(KST) — cron 기본
npm run cluster:day -- --date=2026-08-23
npm run cluster:day -- --from=2026-06-01 --to=2026-08-23
npm run cluster:day -- --all                           # 기사가 존재하는 모든 날짜
```

`--all`이 필요한 이유: RSS `pubDate`가 깨진 기사 때문에 2023-03 날짜가 섞여 있어, 날짜 범위로
돌리면 기사가 없는 1,200여 일을 헛돌며 DB를 그만큼 왕복한다.

## 대표 제목

그룹 centroid에 코사인 최근접인 기사의 제목을 쓴다(`representativeIndex`). LLM 호출이 0이면서
"첫 기사 제목"보다 대표성이 좋다. `llm-judge.ts`는 남겨 뒀지만 **현재 쓰지 않는다** — HAC가
배치 전체를 보고 나누므로 greedy 시절의 경계 판정이 덜 필요하다.

## 저장 형식

|                     | 이전                            | 현재                              |
| ------------------- | ------------------------------- | --------------------------------- |
| `Article.embedding` | `embeddingJson` 문자열 ≈10KB    | **Float32 raw bytes 2,048B**      |
| `Cluster.centroid`  | `centroidJson` ≈10KB × 11,376개 | **제거** (배치 후 다시 쓰지 않음) |
| DB 크기             | 261MB                           | **109MB** (현재 101MB)            |

`Bytes` 인코딩은 `vector.ts`가 `DataView`로 처리한다. Buffer를 쓰지 않는 이유는 (1) 엔디안 명시
(2) byteOffset 정렬 제약 회피 (3) Prisma 7의 `Bytes`가 `Uint8Array<ArrayBuffer>`라 `Buffer`와
제네릭이 어긋남 — 세 가지다.
